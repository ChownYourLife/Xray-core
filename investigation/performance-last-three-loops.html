How to read the results

Each baseline is the immediately preceding implementation, with earlier optimizations already included. These are incremental, local comparisons—not cumulative benefits. Do not compare latency across loops, add percentages, or infer WAN, full-core or production-traffic throughput.

Recorded environment: Go 1.27, darwin/arm64, Apple M5 Pro. Each primary campaign used eight matched commands and four samples per state. Loops 2 and 3 used temporary-file benchmark overlays; loop 4 used a ./common/buf overlay. The per-loop conditions differ:

Loop 2 · seal fitting singleton plaintext directly

common/crypto/auth.go seals a fitting authenticated STREAM single buffer into a separate owned ciphertext buffer, avoiding the plaintext scratch buffer and copy while consuming the input. The shared path benefits Auth, VMess, padded VMess and classic Shadowsocks without changing packet or multibuffer behavior.

Eligibility is determined by actual framing capacity, not by incidental benchmark shape labels: Auth and VMess fit up to 8174 plaintext bytes, VMessPadding up to 8110, and Shadowsocks up to 8158. For the 64-, 1024- and 2048-byte singleton cases, the stored allocation result is 320 → 160 B/op and 8 → 6 allocs/op. Each API’s own oversized threshold+1, full8192 and multibuffer controls retain their allocation counts.

The verifier independently paired the eight stored commands. Across the 64–2048 fitting singleton cases, paired local time reductions were 18.51–42.69%. These paired estimates are distinct from the state medians below and from the state-median percentage in Appendix 2.

Loop 3 · frame oversized singleton input without plaintext scratch

The next auth.go branch handles an oversized single stream buffer. It passes capacity-constrained frame spans directly to Seal, still producing separate owned ciphertext, so it does not allocate/copy a plaintext scratch buffer. Seal failure is all-or-nothing: no successful prefix is forwarded, and owned data is released. After all seals succeed, the oversized source is released before the downstream write. Fitting singleton, multibuffer and packet paths remain unchanged.

The final-source primary campaign has eight commands, 72 cases and four samples per state. The earlier campaign before the early-source-release change is excluded. For full8192, all eight Auth/VMess/VMessPadding/Shadowsocks × AES/ChaCha cases fall from 392 → 240 B/op and 10 → 8 allocs/op. Larger managed shapes retain the exact observed B/op sets in the full appendix, including pool noise.

Behavior and verification boundary

Real-cipher framing regressions cover managed and unmanaged arbitrary-length input, exact multiples and tails, authenticated lengths, padding, nonce progression and second-Seal errors. Capacity-constrained spans prevent an Authenticator’s scratch append from overwriting future plaintext. An intentionally unsafe-capacity negative control fails the plaintext test, providing evidence that this isolation test discriminates the bug. Ownership checks observe the oversized source released before downstream processing and ciphertext surviving pool churn.

The independent public runtime smoke recorded 88 successful VMess request/response and Shadowsocks roundtrips plus three adversarial successes. Normal and race crypto/Shadowsocks checks passed; the initially cached VMess result was followed by explicit uncached normal and race -count=1 checks. The shared auth source/tests and existing README were the intentional changes; previous optimizations and all other incoming files were preserved, and temporary sources were removed.

Evidence: completion; final-source paired recomputation; public runtime stdout.

Loop 4 · reuse vector storage and track remaining vectors correctly

common/buf/writer.go reuses existing vector payload storage and the net.Buffers header in BufferToBytesWriter. This is not reuse of the payload buffers themselves, and it does not add a concurrency or reentrancy guarantee. The loop also follows actual remaining-vector progress and IsEmpty rather than an aggregate int32 length, fixing a silent skip when aggregate input is at least 2 GiB.

The eight-command ABBAABBA campaign covers 28 shapes with four samples per state. Twenty data-bearing multibuffer shapes save one allocation; eight single-buffer/empty controls are unchanged. The four representative four2048 paths—fallback, tcp, tcp-counter and tcp-dispatcher-counter—show 344 → 320 B/op and 10 → 9 allocs/op.

Allocation-only acceptance. The production writer and benchmark harness match the accepted final versions, but the benchmark binary linked an earlier test layout. Historical timing results were mixed, and later test cleanup could change binary layout. Accordingly, this report makes no final-binary CPU-gain claim and shows no loop 4 timings.

Behavior and verification boundary

The aggregate-length regression uses logical repeated 1 MiB unmanaged views written to io.Discard. It checks correctness, not real multi-GiB TCP transfer, WAN throughput or timing. Tests also cover private vector-write behavior, partial-error progress, exact bytes and statistics, managed ownership release, post-error reuse and closed-TCP empty input.

The independent real loopback/runtime smoke recorded 17 delivered bytes and counter 17. A fallback partial error accepted 3 bytes, then two managed NE/XT vectors produced preNEXT with final counter 7; input ownership was released. A closed TCP writer receiving nil plus a managed empty buffer returned nil, released the empty input and left counter 0.

Final focused checks executed and passed common/buf; proxy/freedom compiled with no tests, and proxy/socks was cached. The common/buf race check executed and passed. Only README, common/buf/writer.go and common/buf/writer_test.go changed; 1169 other incoming files and all preceding optimizations were preserved. The README contract was updated and temporary overlays, scripts, profiles, binaries and runtime sources were removed.

Evidence: completion; final-source/raw recomputation; final focused/race results; multivector runtime stdout.

Numeric rendering and cell provenance

Scalar benchmark numbers use the exact Python JSON-decoded integer string or shortest round-trip float representation (repr); no additional rounding is applied in tables. Unique byte/allocation sets are sorted, deduplicated, and joined with , , for example 320, 321. Approximate percentages in prose follow the cited completion/verifier precision, not a new statistical calculation.

Each benchmark name and numeric benchmark cell carries data-source, data-row and data-field. Source paths are relative to this report’s investigation directory; data-row is the exact benchmark name. Fields are dot paths relative to that selected row. Loop 3’s rows are keyed objects: data-field="name" data-transform="object-key" means the row key itself. Loop 4 sample fields such as samples.A.bytes project the terminal field across the sample array; data-transform="project-sorted-unique" specifies sorting/deduplication. State sets use data-transform="sorted-unique". A and B are baseline and final respectively. Exact benchmark names, including CPU suffixes where stored, are preserved.
